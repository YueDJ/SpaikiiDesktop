多提供商认证与凭据生命周期管理模块（uth.py + credential_lifecycle.py）是 Sparkii CLI 的认证中枢，负责统一管理所有推理提供商的 OAuth 授权码流程、API Key 凭据解析、令牌刷新与凭据一致性维护。uth.py（约 9240 行）是系统中最大的单一模块之一，通过 ProviderConfig dataclass 和 PROVIDER_REGISTRY 集中声明所有已知推理提供商（Nous Portal、OpenAI Codex、xAI、Qwen、MiniMax、Anthropic、Gemini、Bedrock、Vertex、Azure Foundry 等），按 uth_type（oauth_device_code / oauth_external / oauth_minimax / pi_key / ws_sdk / ertex / external_process）分发不同的凭据解析策略。

认证状态持久化在 ~/.sparkii/auth.json 中，使用跨平台文件锁（POSIX 的 cntl 与 Windows 的 msvcrt）实现跨进程并发安全。核心函数 esolve_provider() 通过优先级链选择当前活跃提供商，esolve_*_runtime_credentials() 系列函数处理各提供商特有的令牌刷新逻辑（如 Nous Portal 的 Invoke JWT、Codex 的 OAuth access token 刷新带时间偏移补偿、xAI 的 OAuth 外部流程、Qwen 的 portal 集成）。端点探测方面，模块内置 Z.AI 并行探针、Kimi 前缀路由等智能解析机制。

credential_lifecycle.py（272 行）是凭据写入与删除的单一入口，解决了历史上桌面端 /api/env 端点与 TUI Gateway RPC 仅修改 .env 而遗漏其他存储位置导致的凭据不一致问题（#51071、#59761、#62269）。一个提供商 API Key 可能同时存在于三个位置：~/.sparkii/.env（规范密钥存储）、uth.json 中的 credential_pool 条目（source == "env:<VAR>"）、以及 config.yaml 中的内联镜像（model.api_key、uxiliary.*.api_key、custom_providers[*].api_key）。save_provider_env_credential() 在写入 .env 后同步更新所有镜像，emove_provider_env_credential() 则清除所有三个存储中的引用，同时严格保留 OAuth/device-code/manual/borrowed 类型的凭据条目不被误删。模块还实现了凭据源抑制机制（suppress_credential_source），防止进程环境中残留的旧值在下次加载时重新注入已删除的凭据。
